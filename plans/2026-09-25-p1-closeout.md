## The `N₀` decision for token-ring (deliverable 3)

### The measured cost curve, exactly

`distinct(N) = 3N·2^(N-1)` and `generated(N) = 3·N·(N+1)·2^(N-2) + 1`. TLC's wall-clock tracks
*generated* states (it does one unit of work per generated state), so wall-clock is predicted from
`generated` and the measured per-state rate:

| anchor | generated | wall-clock | rate (s / generated state) |
| --- | --- | --- | --- |
| N = 17 (`README.md:102`) | 30 081 025 | 33.4 s | ≈ 1.11·10⁻⁶ |
| N = 19 (`plans/2026-09-25-bootstrap.md:148-149`) | 149 422 081 | 169 s | ≈ 1.13·10⁻⁶ |

Both anchors agree to ≈2 %, so take the rate as **≈1.12·10⁻⁶ s / generated state**.

### Extrapolation to the 2 h cap

| N | generated | predicted wall-clock | vs 7200 s cap |
| --- | --- | --- | --- |
| 21 | 726 663 169 | ≈ 13.6 min | inside |
| 22 | 1 591 738 369 | ≈ 29.7 min | inside |
| **23** | **3 472 883 713** | **≈ 64.8 min (≈ 1.08 h)** | **inside, 1.85× headroom** |
| 24 | 7 549 747 201 | ≈ 2.35 h | **over** |
| 25 | 16 357 785 601 | ≈ 5.1 h | over |

Cross-check against external throughput: the published EWD998 run at N = 4 did 219 M distinct states
in ≈50 min ≈ 4.4 M states/min (`README.md:31`); token-ring N = 23 is 289 M distinct in ≈65 min ≈
4.45 M states/min. Same order — the model is sound, and 289 M states is routine for TLC 2.19.

### The decision

**`N₀ = 23`.** Predicted: wall-clock ≈ 60–70 min (central ≈ 65 min), `distinct == 289 406 976`
(= 3·23·2²²), `generated == 3 472 883 713`, `left == 0`. `N = 24` is the first value that collides
with the cap (≈2.35 h), so 23 is the largest `N` safely inside.

**What falsifies this choice** (each is a coder-run observation, not a scenario):

1. **The N = 23 run times out** (> 7200 s, `outcome: timeout`) — the per-state rate was optimistic;
   step down to N = 21 (or N = 22) and re-measure. (Not expected: the two anchors agree and the
   EWD998 cross-check matches.)
2. **The N = 23 run completes but with no headroom** (e.g. > 100 min) — the rate was optimistic;
   keep the measurement, record the real wall-clock, and re-decide with the measured number.
3. **A TLC blow-up** — an `OutOfMemoryError` or disk exhaustion in `specs/tla/token-ring/states/`
   despite the disk-backed FPSet/queue. Not expected at 289 M states (EWD998 N = 4 is 219 M), but a
   `df` check before and after the run is the cheap guard.
4. **A non-deterministic distinct count** — `distinct != 289 406 976`. The count is exact and
   deterministic (`-workers 1`); a different number means the spec changed under us, the wrong config
   was selected, or a fingerprint collision (the run's tail prints the "probability TLC did not check
   all reachable states" estimate; at N = 3 it is 7.2·10⁻¹⁷ — negligible). Report and stop.

The N = 23 run is a **coder-run calibration step** (≈65 min), *not* a pytest scenario: a TLC-invoking
scenario must run in about a second (AGENTS.md), and this is an order of magnitude above that. It
appends one Route A row to `results/tlc.jsonl` through the harness. The 5-repetition N₀ result cell
(protocol §4.7, `R ≥ 5`) is the protocol's Route A collection at `N₀`; it is the immediate follow-on
(≈5.4 h of TLC) and is listed as a step with its time cost stated, not folded into the calibration.

## The Bakery task (deliverable 4)

### Which spec revision

A **new bounded atomic-register spec** at `specs/tla/bakery/Bakery.tla`, derived from — not a copy of
— the IJCAR artifact. The imported `specs/tla/ijcar2010/bakery/Bakery.tla` is infinite-state (above),
so the task cannot reuse it. The bounded spec drops `TLAPS` (no `THEOREM`/`PROOF`; the proof stays in
the IJCAR provenance), makes the `flag`/`num` register writes atomic steps, and bounds the ticket
domain to `0..N` (the IJCAR's unbounded `\E i \in {j \in Nat : j > max}` becomes
`\E t \in 0..N : \A j \in P\{i} : t > num[j]`, and the safe-register `repeat`/`k \in Nat`
nondeterminism is dropped). This is exactly the "version … efficient to model check" the artifact's
own comment says the safe-register form lacks (`Bakery.tla:44-45`).

Reference design (the coder types this exactly; the planner owns the contract, not the `.tla`):

```tla
----------------------------- MODULE Bakery -----------------------------
EXTENDS Naturals

CONSTANT N
ASSUME N \in Nat /\ N >= 2

P == 1..N

VARIABLES num, flag, pc

TypeOK ==
    /\ num \in [P -> 0..N]
    /\ flag \in [P -> BOOLEAN]
    /\ pc \in [P -> {"idle", "doorway", "wait", "crit"}]

Init ==
    /\ num = [i \in P |-> 0]
    /\ flag = [i \in P |-> FALSE]
    /\ pc = [i \in P |-> "idle"]

\* lexicographic ticket order; ties cannot occur (tickets are strictly increasing),
\* the tie-break is kept defensively and matches the IJCAR LL
LL(i, j) ==
    \/ num[i] < num[j]
    \/ /\ num[i] = num[j]
       /\ i <= j

SetFlag(i) ==
    /\ pc[i] = "idle"
    /\ flag' = [flag EXCEPT ![i] = TRUE]
    /\ pc' = [pc EXCEPT ![i] = "doorway"]
    /\ UNCHANGED num

ChooseTicket(i) ==
    /\ pc[i] = "doorway"
    /\ \E t \in 0..N :
         /\ \A j \in P \ {i} : t > num[j]
         /\ num' = [num EXCEPT ![i] = t]
    /\ flag' = [flag EXCEPT ![i] = FALSE]
    /\ pc' = [pc EXCEPT ![i] = "wait"]

Enter(i) ==
    /\ pc[i] = "wait"
    /\ \A j \in P \ {i} : flag[j] = FALSE /\ (num[j] = 0 \/ LL(i, j))
    /\ pc' = [pc EXCEPT ![i] = "crit"]
    /\ UNCHANGED << num, flag >>

Exit(i) ==
    /\ pc[i] = "crit"
    /\ num' = [num EXCEPT ![i] = 0]
    /\ pc' = [pc EXCEPT ![i] = "idle"]
    /\ UNCHANGED flag

Next ==
    \E i \in P : SetFlag(i) \/ ChooseTicket(i) \/ Enter(i) \/ Exit(i)

MutualExclusion ==
    \A i, j \in P : (i # j) => ~(pc[i] = "crit" /\ pc[j] = "crit")

Spec == Init /\ [][Next]_<<num, flag, pc>>
=============================================================================
```

### Property

`MutualExclusion` (safety): "no two distinct processes are simultaneously in their critical section"
— the same operator the IJCAR proof establishes (`THEOREM Spec => []MutualExclusion`).

### The mutant and its expected violation

`specs/tla/bakery/BakeryMutant.tla` = the bounded spec with the `Enter` guard weakened to drop the
ticket/`num` check, keeping only the flag check:

```tla
Enter(i) ==
    /\ pc[i] = "wait"
    /\ \A j \in P \ {i} : flag[j] = FALSE          \* MUTANT: ticket ordering dropped
    /\ pc' = [pc EXCEPT ![i] = "crit"]
    /\ UNCHANGED << num, flag >>
```

Two processes in `wait` (both with `flag = FALSE` and non-zero tickets) now each satisfy the guard and
enter together. **Expected**: `outcome: violation` with the log text
`Error: Invariant MutualExclusion is violated.` and a trace showing two processes at `pc = "crit"` —
the negative control, caught by the same rig (this is the token-ring-mutant analogue: dropping one
guard that the safety property depends on).

### Bakery `N₀`

The ticket domain `0..N` per process makes the state space grow roughly as `(N+1)^N · poly(N)` — far
faster than token-ring's `3N·2^(N-1)` — so `N₀` is expected in the single digits (N = 4–6). It is
**measured, not predicted**: the coder runs `N = 3, 4, 5, …` through the harness (each a coder-run
step; N = 3 and 4 are seconds, N = 5+ minutes) until a run exceeds the 2 h cap, and fixes
`n0 = <largest N that completed>` in `tasks/bakery.json`. The contract pins `n0` as "set and
consistent with a shipped instance", not a specific number (unlike token-ring, where `N₀ = 23` is
settled by arithmetic above).

## Decisions

### D1 — token-ring `N₀ = 23`

Stated with arithmetic above. The manifest gains a second instance (`N = 23`), keeping `N = 3` as the
fast instance the existing scenarios use.

**Concurrent-load caveat (observed during the calibration run).** An external pytest TLC suite
(`WfxModel`, absent from this repository) ran concurrently with the N = 23 calibration on the shared
host, so that row's `wall_clock_s` is contaminated and is treated as an upper bound, not a clean
measurement. The `distinct`/`generated`/`depth` counts are deterministic and unaffected — they remain
the authoritative N₀ confirmation. The authoritative N = 23 wall-clock comes from the quiescent
5-repetition result cell (protocol §4.7), run with no concurrent TLC. A timeout observed *while that
external suite is running* is a measurement-environment failure, not a D1 falsifier; only a timeout
under quiescence falsifies N₀ = 23.

**Measured (2026-09-25) and re-decided: N₀ = 23 holds.** The calibration row landed: `wall_clock_s =
6748.6` (112.5 min), `distinct = 289406976` — exact (`3·23·2²²`) — `outcome: success`, inside the 7200 s
cap by 451 s (6.3 %). The wall-clock is outside the plan's 100-min "no headroom" band, and the implied
rate is ≈1.94e-6 s/generated state, not the 1.12e-6 extrapolated from N = 19 (the discrepancy: the
per-state rate grew ~1.7× from N = 19 to N = 23 — partly the concurrent WfxModel load recorded above,
partly genuine per-state growth with N). Re-decision: **N₀ stays 23** — it completed inside the cap
(protocol §4.2's letter: the largest N inside the cap), the exact distinct count confirms the
state-space model, and the wall-clock is an upper bound (the quiescent rate is faster, so the true
margin exceeds the recorded 6.3 %). N = 24 at the measured rate is ≈14 700 s (245 min), over the cap.
The 6.3 % margin is accepted deliberately.

### D2 — the token-ring manifest ships both instances; the fast scenarios select `N = 3` explicitly

`tasks/token-ring.json` becomes `instances: [{param_N: 3}, {param_N: 23}]`, `n0: 23`. The runner
errors on "several instances" when none is selected (`harness/tlc_run.py:302-307`), so the two

done in this session; it is not a red-green scenario because the behavior it pins (`N = 3`, 36
distinct) is unchanged.

### D3 — Bakery is a new bounded atomic-register spec, not a reuse of the IJCAR file

Decided from evidence (the IJCAR spec is infinite-state and `EXTENDS TLAPS`; see "Where the work
stands"). The IJCAR `Bakery.tla` remains the published-proof provenance and the Route B audit
reference for *why* the model is simplified. Consequence: the equivalence audit (P2) will state the
Route A reference is the *atomic-register* bakery, while the published IJCAR proof is over the
*safe-register* bakery — that gap is recorded, never papered over.

### D4 — ticket bound = `N`

`num ∈ 0..N`, the same `N` as the instance parameter. A process with `max(others) = N` has no fresh
ticket inside the bound, so that doorway step is disabled (a bounded-model deadlock, not a bug). This
under-approximates re-entry executions; for the *safety* property `MutualExclusion` it is the standard
bounded projection (a counterexample needs at most `N` distinct ticket values). Analogous to EWD998's
`StateConstraint` (`K = C = 3`, `Q = 9`).

**Deadlock and `CHECK_DEADLOCK FALSE` (decided on the coder's plan question).** The bound makes a
deadlock state *reachable* — e.g. N = 3: `SetFlag(1); SetFlag(2); SetFlag(3); ChooseTicket(1)` with
`t = 3` leaves `pc1 = "wait"` holding the max ticket while `pc2 = pc3 = "doorway"` can no longer pick a
ticket `> 3` inside `0..N`, and no other action is enabled. This is a bound artifact, not a bug: the
unbounded IJCAR model has no deadlock because a larger `Nat` always exists. Deadlock-freedom is a
liveness concern and out of scope (protocol §11 decision 4), so the three Bakery configs carry
`CHECK_DEADLOCK FALSE` — the same two lines the EWD998 configs already use (`EWD998.cfg:19-20`) — so
TLC checks `MutualExclusion` and does not report the spurious deadlock as an `error` (which would also
mask the mutant's `violation`). This is a config entry, not a harness change; `read_cfg` reads only
`CONSTANT` and `INVARIANT`, so it is unaffected. The token-ring configs have no such line because
token-ring has no reachable deadlock.

**Cosmetic conformance (accepted).** The coder wrote `ASSUME NAssumption == N \in Nat /\ N >= 2` and
`vars == <<num, flag, pc>>` with `Spec == Init /\ [][Next]_vars`, matching the token-ring idiom rather
than the unnamed forms in the reference above. Accepted: they are behaviour-neutral and consistent
with the repo's own convention.

## Design question for the user (deliverable 5)

One material choice, for awareness rather than a blocker:

**The Bakery system is the atomic-register, bounded-ticket variant, not the IJCAR safe-register
model.** Options:

1. **Atomic-register (recommended).** `flag`/`num` writes are atomic steps; the ticket domain is
   `0..N`. Finite-state, standard, TLC-checks fast, and the mutant (dropping the ticket check) is
   caught cleanly. Consequence: the Route A reference is the *simplified* bakery; the equivalence
   audit (P2) records that the published IJCAR proof is over the safe-register model, so "the same
   system" is the atomic bakery on both Route A and Route B, with the safe-register proof as prior art
   rather than the Route B target.
2. **Safe-register, bounded.** Keep the IJCAR `repeat`/`k \in Nat` write nondeterminism but bound it
   (`k \in 0..N`, `i \in (max+1)..N`). More faithful to Lamport/IJCAR, but the `repeat` loops multiply
   the state space (smaller `N₀`), the "fresh ticket ≤ N" boundary needs an explicit guard, and the
   derivation is materially messier. Consequence: `N₀` shrinks and the mutant/positive runs are slower
   to calibrate, with no gain for the P1 purpose (calibrating `N₀` and validating the rig + mutant).

The recommendation is option 1 on three grounds: the IJCAR artifact's own comment says the
safe-register form "makes model checking infeasible" and points at an easy-to-check variant
(`Bakery.tla:44-45`); P1's purpose is calibration and end-to-end mutant validation, not a
safe-register showcase; and Route B (P2) will port whichever Route A uses, so option 1 keeps the two
routes on one consistent reference with the safe-register model preserved as provenance. If the
experiment later wants a "faithful to Lamport" safe-register comparison, that is a P3 task, not this
one.
